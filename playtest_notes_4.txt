Date: 2026-09-13
Method: live playthrough via the godot-ai MCP session, driven through
editor_manage(game_eval) rather than mouse/keyboard input simulation (per

CONFIRMED WORKING — RUN MODIFIER SYSTEM (the "roguelike" per-run variance)
============================================================================
File: src/classes/run_modifier.gd, src/autoload/run_modifier_registry.gd,
src/classes/brewery.gd (run_modifier, get_effective_raid_threshold(),
_on_buy_ingredient/_on_sell_ingredient), src/classes/brew_resolver.gd
(ingredient_price_multiplier).

Sampled all 5 modifier resources directly and verified
get_effective_raid_threshold() = roundi(100 * avi_threshold_multiplier)
for each:

  Modifier            avi_mult   price_mult   effective_raid_threshold
  Tavallinen keikka   1.0        1.0          100
  Kallis tori         1.3        1.4          130
  Kireä AVI           0.7        0.8          70
  Löysä valvonta      1.5        1.0          150
  Ainepula            1.0        1.5          100

All five compute correctly — no off-by-one or rounding surprises at any
of the five multiplier values in play.

Verified the price multiplier live, not just as arithmetic: forced fresh
runs until landing on "Kireä AVI" (0.8x), then bought 2kg Pilsner malt
(base_price 2 €/kg) through the real GUISignals.buy_ingredient path.
Charged exactly 3 € (roundi(2*2*0.8) = 3.2 -> 3), money went 20 -> 17.
Also confirmed BrewResolver.resolver.ingredient_price_multiplier (the
cached copy the cost-preview UI reads) stayed in sync with the live
run_modifier's value, as its own docstring promises.

Verified the AVI threshold isn't just cosmetic: with the same "Kireä
AVI" run, pushed risk to 69 (no raid) then to 70 — the raid fired
exactly at the modifier-adjusted threshold, not the hardcoded 100. This
is new behavior since the modifier system was wired into
_check_for_avi_raid() by way of get_effective_raid_threshold(), and it
holds up correctly under real play.

No design issues found here — the modifier system does exactly what its
own docstrings claim, at every value it can roll.

Survived ending (day 15, reputation 50, money 50): TimeManager.
force_advance_day() correctly fired "LEGENDA!" with both stat lines and

so rank #1 / "UUSI ENNÄTYS!" showed again, correctly). Both "Uusi
yritys" and "Jatka pelaamista (ei tilastoihin)" shown, as expected only

Continue-past-survival: pressed continue programmatically
(_on_continue_button_pressed()) — has_continued_past_survival flipped to

showing a rank for an entry that doesn't actually exist on the list.
This confirms the has_continued_past_survival guard added to
GameEndWindow this session stays honest with what LeaderboardManager
actually records, instead of drifting into a display bug of its own.

Main-menu leaderboard window: opened via the real button handler,
screenshotted with both recorded entries present. Displayed:

  #1  Selvisi — 15 pv, 50 mainetta, 0 pulloa (2026-09-13T10:27:33)
      Kireä AVI — pisteet: 2000
  #2  Jäi kiinni — 1 pv, 0 mainetta, 0 pulloa (2026-09-13T10:26:09)
      Kireä AVI — pisteet: 100

Correctly sorted by score descending, correct Finnish ending labels
("Selvisi" / "Jäi kiinni"), correct modifier_name per entry, close

Minor polish nit, not a bug: the date field is Godot's raw

custom formatting; this one line reads like a debug timestamp. Worth a
pass to show just a date (or "tänään"/"eilen") if this list is meant to
feel like a trophy case rather than a log.

DEFENSIVE CHECK: SIGNAL CONNECTIONS ACROSS SCENE RELOADS
============================================================
Worth calling out since this session alone triggered ~6 full main.tscn
reloads in quick succession (restart-after-busted, restart-after-
bankrupt, "Aloita uusi peli" from the menu, etc.) — exactly the kind of
repeated churn that could reveal a leaked signal connection if any
per-scene node connected to a project-lifetime autoload signal without
ever disconnecting. Directly inspected
BrewerySignals.get_signal_connection_list("brewery_state_changed") after
all that churn: 11 connections, a plausible count for one live scene's
worth of listeners (top panel, daily goals, gui.gd, brewery/shop/
warehouse views, audio manager, etc.), not an accumulating count from
old freed scenes. Also checked
SpecialEventManager.get_signal_connection_list("special_event_triggered")
directly by object identity: exactly one connection each to
AudioManager, DialogView, and DevConsole — no duplicates. (A duplicate
"Erikoistapahtuma: ..." console log line during testing briefly looked
like a leaked connection; it wasn't — real session wall-clock time had
just crossed the real 300s automatic special-event timer interval at
almost the same moment as a manually forced one, producing two genuine,
separate events.) No leak found. Godot's automatic connection cleanup on
node free appears to be working as expected for this codebase's signal-
heavy architecture.


TESTING METHODOLOGY CAVEATS (not gameplay bugs)
===================================================
- BrewEngine.start_new_game() was called directly via game_eval once
  (to reroll the run modifier without waiting on randomness) without
  the scene reload that always accompanies it in real code (main_menu.gd
  and game_end_window.gd both immediately follow it with
  change_scene_to_file()). Doing so left the still-open
  SaleReceiptLogWindow showing the previous (now-discarded) run's
  receipts, since nothing about start_new_game() itself tells that
  window to refresh. This is unreachable through any real player action
  — every real code path pairs start_new_game() with an immediate scene
  reload, which would recreate that window empty — so it is not being
  filed as a bug, just documented so it isn't mistaken for one later if
  someone reads this in isolation.
- All unit tests (42, across 6 suites including the new
  test_leaderboard_manager.gd) were confirmed green earlier in this same
  session, before this playthrough began; nothing touched during the
  playthrough itself edited any .gd/test file (only live game state via
  game_eval, plus the one dead .tscn deletion above), so that result
  should still hold, but a fresh test_run was not re-executed at the very
  end of this session to confirm it directly.
