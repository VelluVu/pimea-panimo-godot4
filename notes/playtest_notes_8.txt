TESTING METHODOLOGY NOTES (not gameplay bugs, worth recording)
=========================================================================
- Reconfirms playtest_notes_5/_6/_7's game_eval fragility finding, with a
  new trigger: an eval script whose own `await` runs past the tool's ~8s
  per-call budget (EVAL_HUNG) crashes the whole game into the same
  unrecoverable debugger break a syntax/runtime error does — not just
  parse errors or bad indentation. So does an ordinary uncaught runtime
  error in an eval script (e.g. calling a method on a null find_child()
  result) even with no await in flight. Both happened this session; both
  needed project_manage(stop) + a fresh project_run, exactly as documented
  — resume() does not help either case. Practical takeaway used for the
  rest of this session: keep any single eval's awaited duration under ~6s
  and poll in a follow-up call instead of one long await.
- Real wall-clock time elapses between separate MCP tool calls (thinking
  and round-trip latency), and the game keeps running in the background
  the whole time — reputation-scaled walk-in timers (30-90s range at
  reputation 0) can and did fire organically between calls with no
  explicit wait on my part. Not a bug, just worth knowing before assuming
  a customer who "appeared out of nowhere" is a spawn-logic problem.
- The dev console's developer-mode commands (sell/customer/group/special/
  raid/day) were confirmed by reading dev_console.gd to route through the
  exact real gameplay code — CustomerManager.process_auto_sale(),
  CustomerManager.spawn_normal_customer(), TimeManager.force_advance_day(),
  Brewery.add_risk() — not simulated shortcuts, so exercising them is
  equivalent to a player action for everything downstream of that call.
- A standalone `x if cond else y` GDScript ternary written as a bare
  statement (used once in one of this session's own throwaway eval
  scripts, checking has_method() before a call) logs "Standalone ternary
  operator" + "not mutually compatible" warnings through the editor log
  channel with path="" line=0 — a red herring the first time you see it;
  it's the dynamically-compiled eval script being warned about, not
  anything in the actual project source. Confirmed nothing in src/scenes
  matches that pattern.

MINOR POLISH NOTED IN PASSING (not bugs)
=========================================================================
- Two typos in player-visible-adjacent (console/log) strings, both in
  src/autoload/string_container.gd: line 113's WITHDRAW_INVALID_AMOUNT_ERROR
  ("withraw failed... withraw amount") and line 127's
  SUCCESFULL_BREW_MESSAGE ("Succesfull brew batch"). Neither reaches a
  normal player (console/print only), but they're one-line fixes.
- The player-facing "keitä <resepti>" dev-console command always logs
  "Keitetään: <name>" the instant it fires GUISignals.start_brewing,
  regardless of whether the brew actually succeeds — reproduced by
  running it on a fresh game with nothing bought yet: it printed
  "Keitetään: Kotikalja (perusresepti)" and looked like it worked, while
  the real result (confirmed via the game log) was three straight
  failures — "table has no ingredients", "not enough ingredients" — with
  nothing on screen telling the player that. `_cmd_keita()` in
  dev_console.gd would need to check start_brewing's actual outcome (or
  at least whether the table has anything on it) before claiming success.
- A level-up popup and the run-ending window can land on top of each
  other (happened here when the last day's final sale crossed both a
  level threshold and the survival bar in the same tick) — not broken,
  dismissing the level-up correctly reveals the end screen underneath,
  but worth a deliberate priority decision (defer the level-up choice
  until after the end screen, most likely) rather than leaving it to
  z-order luck.
