TESTING METHODOLOGY NOTES (not gameplay bugs, worth recording)
=========================================================================
- Reconfirmed the standing game_eval fragility finding repeatedly this
  session: any compile error (bad syntax), runtime error (wrong
  property/method name, e.g. TimeManager.current_day instead of
  Brewery.current_day, or Inventory.owned_ingredients instead of
  Inventory.items), or null-access from a guessed node path freezes the
  whole game session (game_status.status="break") — stop+relaunch is
  required every time, resume() does not help. Hit this 5 times in one
  session from guessing property/signal/node names instead of reading
  the source first; reading the target script before every eval call
  (property names, signal names, exact node paths from
  get_ui_elements) is the only reliable way to avoid it.
- New finding this session: project_manage(op="stop") — the MCP
  equivalent of the editor's Stop button — hard-kills the running game
  process rather than sending it an OS-level window-close request. Since
  SaveManager only autosaves from get_tree().root.close_requested (see
  src/autoload/save_manager.gd _ready()), stopping the game this way
  never triggers that autosave, so any progress made since the last
  real save (day change, manual Options save, or an actual window
  close) is silently discarded on the next "Jatka peli" — confirmed by
  money/reputation reverting from a post-sale 271.6€/76 back to the
  original continued save's 273.5€/71 after an MCP-triggered
  relaunch. This is a testing-environment quirk, not a player-facing
  bug (a real player closing the window normally goes through
  close_requested and does autosave) — but it means future MCP
  playtest sessions can't treat a post-crash "Continue" as resuming
  the crashed session's actual state, and should re-verify brewery
  stats via a safe eval read immediately after continuing rather than
  assuming continuity.
- emit_signal("pressed") on a freshly-fetched button node occasionally
  had no visible effect when called back-to-back with a scene
  transition on the same eval tick (the DailyGoalsPanel toggle button's
  first press didn't expand the panel); adding `await
  get_tree().process_frame` after the emit before reading the result
  back made every subsequent toggle land correctly. Worth building
  into the standard interaction pattern for this kind of test, on top
  of the already-known input-simulation-unreliable finding.

BUG FOUND — DAILY GOAL PROGRESS NEVER SURVIVES A SAVE/CONTINUE
=========================================================================
DailyGoalManager's per-slot state (active_goals, _progress,
_reputation_baseline, _effective_target) is held entirely in that
autoload's own memory and is never written by SaveManager.save_game()
(which only serializes BrewEngine.current_brewery — see
src/autoload/save_manager.gd). SaveManager.load_game() always
constructs a brand-new Brewery instance via
ResourceLoader.load(..., CACHE_MODE_IGNORE); DailyGoalManager's
_on_brewery_state_changed() treats any new Brewery instance as "a
fresh run just started" (per its own docstring) and unconditionally
resets and re-rolls all 3 active goals from scratch.

Net effect: every time a player quits to the main menu (or fully
closes the game — the game explicitly autosaves on window close, see
SaveManager._on_close_requested()) and picks "Jatka Peliä", whatever
progress they'd made on the current day's 3 daily goals is silently
discarded and replaced with a brand-new random set at 0 progress, with
no indication this happened. Reproduced 3 times this session across
independent load cycles (each producing a different random goal
trio). Money, reputation, day, risk, level, and warehouse contents all
correctly survive the same save/load — only the daily goals reset,
which reads as inconsistent since everything else about a day in
progress carries over.

Given a default day is 300 real-time seconds, this is very reachable
in normal play (pause, alt-tab out and back rarely matters, but
actually closing the app and resuming later is an explicitly supported
flow) and undercuts the goal system's "quest tracker" framing — a
player who checks progress, quits for a break, and resumes will find
their tracked goals silently swapped out from under them.

Suggested fix direction (not implemented, playtest-only per this
session's scope): serialize active_goals (by id/resource path),
_progress, _reputation_baseline, and _effective_target onto Brewery (or
a dedicated exported sub-resource) alongside the rest of the run state,
and have DailyGoalManager restore from it in _on_brewery_state_changed()
instead of unconditionally re-rolling whenever brewery != _tracked_brewery
does the load path also need to distinguish "loaded save" from "genuinely
new run" for this to work correctly.
