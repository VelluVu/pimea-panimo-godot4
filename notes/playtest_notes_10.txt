Pimeä Panimo — Full-Loop Playtest (Warehouse Distribution, Daily Goal
Overhaul, Brewing "Täytä resepti", UI Mouse-Filter Sweep)
Date: 2026-09-16
Method: live playthrough via the godot-ai MCP session, driven through
editor_manage(game_eval) executing real GDScript against the running
game, real button presses (emit_signal("pressed") on the actual node,
not GUISignals shortcuts) wherever the row/button in question was the
thing under test, and dev-console commands for anything that needed a
customer/event/raid on demand — same methodology as every prior playtest
note in this series. Loaded the player's real continuing save via
"Jatka peli" rather than a fresh game, so every number below is real
save state, not synthetic. This is a full-loop pass (menu → sales →
warehouse distribution → daily goals → level-up → special event → raid →
day-end → fresh day) rather than one isolated feature, specifically to
catch cross-system interactions the last few feature-scoped sessions
(playtest_notes_9 and everything after it) couldn't.


TESTING METHODOLOGY NOTES (not gameplay bugs, worth recording)
=========================================================================
- Reconfirmed the standing game_eval fragility finding with a fresh
  trigger: an inline `func` declared mid-script inside an eval body
  (while probing RecipeLibraryWindow's node tree) compiled to a real
  parse error and froze the whole game the same way a runtime error
  does — stop+relaunch, resume() does not help, same as every prior
  session's finding.
- RecipeLibraryWindow's rows_vbox is reused for both the style-list and
  the per-style recipe-list views (same VBoxContainer, contents cleared
  and rebuilt on each navigation). A style row is a single Button whose
  full multi-line description (name, ABV, EBC/IBU, hop/malt notes) lives
  directly in Button.text — it has no child Label to probe, so
  `row.get_children()` on a style row correctly returns empty. Worth
  knowing before assuming an empty children list means a broken row.

CONFIRMED WORKING — DAILY GOALS (day-scaling, variety, new type)
=========================================================================
- Forced a SHIP_TO_BAR goal (base target 10) into an active slot on the
  real save's day 3: DailyGoalManager.get_effective_target() correctly
  returned 12 (10 * (1 + 0.08*2) = 11.6 → 12), matching the 8%/day
  formula exactly against a real day value, not just the synthetic
  day-10/20 checks from the implementation session.
- Real 31-bottle shipment (above) pushed that goal past its 12-bottle
  target and resolved it successfully through the real signal chain.
- Genuinely useful edge case found FOR FREE by this test: a second,
  independently-rolled "Vie baariin" instance (the harder 25-target
  tier) happened to already be active in a different slot at the same
  time. The same single 31-bottle shipment satisfied both simultaneously
  — both resolved correctly and independently (their own effective
  targets, own progress counters, own scaled rewards, both rerolled
  their slots afterward) with no cross-talk between them. Confirms the
  per-slot int tracking (_progress/_effective_target arrays) stays
  correct even when two instances of the same goal_type are active at
  once, which the pool design always allowed but hadn't been exercised
  live before.
- Day-end reroll re-scales correctly for the new day: on day 4, a fresh
  "Mainetta" goal (50-base tier) came up with effective target 62 (50 *
  1.24), and a fresh "Rahaa" goal (100-base tier) came up with 124 (100
  * 1.24) — both exactly matching day 4's multiplier.
- DailyGoalsPanel's two independent section-collapse arrows (added this
  session) still behave correctly after a real day change and several
  real goal reassignments in between — no stale collapse state, no
  cross-section leakage, confirmed via real button presses both before
  and after the day-4 rollover.

MINOR POLISH NOTED IN PASSING (not a bug)
=========================================================================
- The "make goal text as short as possible" pass earlier this session
  means every tier of the same goal type now shares one identical
  goal_name (e.g. both the 10- and 25-bottle SHIP_TO_BAR goals read
  "Vie baariin"; same for the two SELL_BOTTLES/REPUTATION_GAIN/
  EARN_MONEY tiers). Confirmed live in the two-simultaneous-"Vie
  baariin"-goals case above: the underlying tracking never confused the
  two, but a player glancing at the panel sees two lines with the exact
  same words and has to read the X/Y numbers closely to tell them apart
  — the numbers alone do carry enough information, but the name no
  longer helps. Worth a follow-up tuning pass only if real play makes
  this feel ambiguous rather than just terse.
