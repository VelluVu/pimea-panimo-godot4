TESTING METHODOLOGY NOTE (not a gameplay bug, but a real methodology gap
that produced a false crash on the first attempt — worth recording)
=========================================================================
The game does NOT boot straight into the gameplay scene. editor_state's
current_scene reports "res://scenes/main.tscn", but that reflects the
scene open in the editor, not the scene actually running — at runtime
the project boots into MainMenu.tscn, which only calls
get_tree().change_scene_to_file("res://scenes/main.tscn") after the
player clicks "Aloita uusi peli" and picks a run modifier
(main_menu.gd:_on_modifier_chosen). CustomerSpawner (and everything else
that lives under main.tscn's WorldYSort) does not exist until that scene
swap happens.

My first attempt called BrewEngine.start_new_game() directly via
game_eval (skipping the menu) and then immediately fired the real
GUISignals.start_brewing signal — the brew succeeded, but the resulting
BrewerySignals.beer_brewed signal triggered CustomerManager._on_beer_
brewed() -> spawn_normal_customer() -> active_spawner._on_walk_in_timer_
timeout(...), and active_spawner was still null (CustomerSpawner had
never been instantiated), which crashed the whole game into an
unrecoverable debugger break — the same class of failure playtest_notes_
5/_6 already documented (project_manage(stop) + fresh project_run
required, not resume()).

Confirmed via a polling loop that this was NOT a frame-timing race —
CustomerManager.active_spawner stayed null even after a 5-second wait,
because the node genuinely doesn't exist yet without the menu's scene
swap. Fix for the test: call get_tree().change_scene_to_file(
"res://scenes/main.tscn") myself after start_new_game(), same as the
menu does, then wait for active_spawner to become non-null before
driving any brewing signals. After that, every following test ran clean.

Applied one small defensive fix anyway (cheap, same philosophy as the
DialogView is_instance_valid() guard from playtest_notes_6): src/
autoload/customer_manager.gd's spawn_normal_customer() and
spawn_group_event() now both null-check active_spawner before calling
into it, instead of assuming it's always set by the time either fires.
Given the real menu flow always instantiates CustomerSpawner before a
brew is possible, this likely isn't reachable by a real player today —
but it costs nothing and prevents the exact crash this test hit if that
ordering ever changes (e.g. a future "quick restart" or save/load path
that reuses an old CustomerManager state).

FOUND DURING TESTING, NOT A BUG: REPUTATION-GATED HOPS SILENTLY NO-OP
WHEN BOUGHT OUT OF ORDER (working as designed, confirmed via source)
=========================================================================
File: src/classes/brewery.gd (_on_buy_ingredient), scenes/ui/
ingredient_option_button.gd, src/resources/ingredients/hops/*.

First pass at the Pale Ale / IPA / Amber Ale rows above failed (all
three silently produced "Kotikalja" at quality 1.0, IBU 0) on a fresh
brewery with reputation 0. Root cause: Cascade (min_reputation 15),
Centennial (min_reputation 20), and Chinook (min_reputation 20) all
failed their GUISignals.buy_ingredient call silently — _on_buy_
ingredient() just print()s INGREDIENT_LOCKED_ERROR and returns, no
signal, no toast — so the hops never entered inventory, never made it
onto the brew table, and the brew matched nothing.

This is NOT a bug: ingredient_option_button.gd's populate_ingredient_
option_menu() already disables the dropdown entry and shows "??? –
vaatii mainetta: N" for any hop the player's current reputation hasn't
unlocked (confirmed by reading the code directly, lines 102-114) — a
real player literally cannot select Cascade/Centennial/Chinook from the
shop UI below reputation 15/20/20, so this silent-no-op path is only
reachable by bypassing the UI the way this test's signal-driven
methodology does. It does explain why the user's original bug report
(which used Cascade + Centennial) only surfaced after they'd already
built up reputation past 20 — a fresh day-1 player physically can't
reach that exact repro. Re-ran the three rows with reputation manually
set to 25 first; all three then passed cleanly (see table above).

Separately, this reconfirms a design point already documented in
playtest_notes_2.txt (2026-09-11/12): an unmatched brew intentionally
falls through to a flat quality=1.0 "Kotikalja"-branded result
(BrewResolver.resolve_brew_style()'s failed_result branch,
is_matched=false) rather than a punishing or clearly-labeled failure —
that was a deliberate fix at the time ("every new player's first,
safest brew comes out looking like a mistake" was the original
complaint it solved). Still working exactly as documented; not a
regression, not touched this session.

VERDICT
==========
The beer-style resolver work holds up under the real brew-button signal
path, not just synthetic testing: all 10 sampled styles (including both
newly-fixed collisions and both range extremes) matched correctly with

CustomerManager is cheap insurance against the same failure shape as

red herring — the shop UI already prevents it correctly; it was only
reachable because this test drives signals directly instead of clicking
through the UI.
