Date: 2026-09-16
Method: live playthrough via the godot-ai MCP session, driven through
editor_manage(game_eval) executing real GDScript against the running
game, plus a real automated test_run pass — same methodology as
playtest_notes_2 through _8 (OS/engine-level input simulation is
unreliable in this environment). Loaded the player's actual continuing
save (not a fresh game) so reputation/money/existing batches were real,
not synthetic. Scope: today's two new warehouse actions — bulk-selling a

button nodes in the live scene tree, not just via GUISignals.emit().


TESTING METHODOLOGY NOTES (not gameplay bugs, worth recording)
=========================================================================
- New finding this session: game_eval runtime mutations (e.g. appending a
  synthetic BrewBatch to inventory.brew_batches for a screenshot) do NOT
  leak into the player's persisted save file. Confirmed by seeding a
  batch, stopping the project (no explicit save call), relaunching, and
  reloading the same save — the synthetic batch was gone, only the
  player's real pre-existing batches remained. project_run's
  autosave=true flag only covers MCP *editor scene* mutations, not
  SaveManager's game-save data. Practical takeaway: this class of live
  testing is safe to run against a real save without fear of
  contaminating it, as long as nothing explicitly triggers a save
  mid-test.
- Reconfirmed playtest_notes_8's game_eval fragility finding with a new
  trigger of its own: get_tree().root.find_children("*", "SomeName",
  true, false)[0] on a *plain node name* (not a registered class_name)
  returns an empty array and indexing [0] crashes the whole game into an
  unrecoverable debugger break, same as any other uncaught eval runtime
  error — needed project_manage(stop) + relaunch, resume() does not help.
  find_children's type filter only matches class_name-registered types;
  a plain scene-tree node name needs find_child(name, true, false)
  instead. Every later lookup in this session bounds-checked the result
  before indexing specifically because of this.
- test_run (88 tests, 15 suites) stayed fully green after all of today's
  changes (BarContact, CustomerRegistry's new pool, both Brewery
  handlers, both new panel scripts) — expected, since none of today's
  new code is covered by an existing suite yet (see IMPROVEMENT
  SUGGESTIONS below).


CONFIRMED WORKING — BULK-SELL
=========================================================================
- Real "Myy" button press (not a signal-emit shortcut) on a real save's
  IPA batch (10 bottles, current_quality 0.1 — a spoiled/declining
  batch): paid out exactly 0.8 EUR and removed the batch from inventory.
  Matches Brewery.BULK_SELL_RATE (0.5) * raw_cost_per_bottle *
  quality_factor (clamped, so a 0.1-quality batch pays a small fraction
  of raw cost) exactly as designed — a real spoiled batch genuinely nets
  less than it cost to brew, confirming the original design ask ("should
  not be very high, and might even be worse than ingredient costs if
  quality is lower or dropping") holds under real play, not just in the
  isolated formula check from implementation.


CONFIRMED WORKING — SHIP TO BAR
=========================================================================
- Real "Vie" button press on a real save's Alkoholiton IPA batch (32
  bottles, quality 0.8) shipped to the default-selected bar (Kulman
  Kuppila, unlocked at reputation 0): paid out 32.8 EUR and added exactly
  4 risk (Kulman Kuppila's risk_per_shipment) — the trade-off side of the
  mechanic confirmed live, not just via direct signal emission.
- BarContactOptionButton's locked-item behavior confirmed by actually
  dropping the save's reputation to 20 and emitting brewery_state_changed
  through the real signal: Kultainen Tynnyri (needs 60) and Yökerho Varjo
  (needs 30) immediately switched to the disabled "??? – vaatii mainetta:
  N" label (correctly reusing StringContainer.INGREDIENT_LOCKED_LABEL,
  the same string IngredientOptionButton uses in the shop), while Kulman
  Kuppila stayed selectable and remained the picker's current selection.
  Restoring reputation to 79 re-enabled both entries immediately and kept
  the existing selection rather than resetting it — matches
  IngredientOptionButton's own "don't disrupt the player's pick"
  behavior that this control was deliberately modeled on.
- Brewery._on_ship_batch_to_bar_requested()'s reputation guard (silent
  refusal below required_reputation) is real defense-in-depth here: the
  UI already prevents selecting a locked bar, so this path isn't reachable
  through normal play, but it means a future UI regression that ever lets
  a locked bar get selected would still fail safely rather than letting
  the player ship to a bar they haven't unlocked.

IMPROVEMENT SUGGESTIONS
=========================================================================
- No player-facing feedback on either action yet. BrewerySignals.
  batch_bulk_sold and keg_shipped_to_bar both fire with the exact payout
  (and risk, for shipping) but nothing currently listens to them — a real
  sale gets sale_tip_gained/reputation_popup_requested-style "+X €"
  popups (see DialogView), bulk-sell and ship-to-bar currently don't.
  Worth wiring a small popup/toast (SaleFlashToast already exists as a
  pattern to reuse) so a click on "Myy"/"Vie" gives the same kind of
  immediate confirmation a real sale does.
- Both actions are single-click-irreversible for the whole batch, no
  confirmation step. A misclick on a large, valuable batch (this session
  moved 32.8 EUR in one press) can't be undone. Given the rest of the UI
  leans toward snappy, no-confirmation actions (dev console, shop
  buttons), this may be an intentional tradeoff, but it's worth a
  deliberate decision rather than an oversight — at minimum the payout
  toast above would let the player see what just happened before the
  next click.
- No dev-console shortcut for either action, unlike buy/sell/brew (osta/
  myy/keitä). A "dump <tyyli>" and "vie <tyyli> <baari>" pair would match
  the existing command surface and speed up future QA passes on this
  system specifically, rather than needing game_eval each time.
- Only 3 BarContact resources exist today, all static and always
  available once reputation clears them. Fine for now, but if this
  system gets expanded later, consider contacts that rotate, expire, or
  unlock via special events for longer-run variety — not a bug, just
  worth flagging as the natural next step for this system's data-driven
  design.
- No automated test coverage yet for Brewery.bulk_sell/ship_batch_to_bar
  payout math or BarContactOptionButton's lock/unlock logic — everything
  in this session was verified live via MCP rather than via tests/. A
  future test_brewery_economy.gd (mirroring test_brew_resolver.gd's
  pure-math style, or test_brewery_xp_curve.gd's static-method
  workaround for Brewery's autoload-dependent _init()) would catch a
  regression in this formula automatically instead of relying on another
  live playtest to notice.
- Row buttons ("Myy"/"Vie") are legible but very cramped at this game's
  640x360 base resolution (28px/23px wide) — functional today, but if
  more per-row actions are ever added to this panel, small icons instead
  of text labels would scale better than shrinking button text further.


VERDICT
==========
Both new warehouse distribution actions work correctly under real play
against the player's actual save — verified through the real button
nodes, not just direct signal emission — with payout math, risk
application, and reputation gating all matching their design exactly.
The full automated suite (88/88) stayed green. No bugs found in the new
systems themselves; the improvement list above is entirely
follow-up/polish work (player feedback popups, a confirmation step,
dev-console parity, and test coverage), not defects.
