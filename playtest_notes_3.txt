Pimeä Panimo — Ending System & New-Economy Playtest Notes
Date: 2026-09-12
Method: live playthrough via the godot-ai MCP session, same approach as the
prior two reports — dev console / GUISignals calls for the real tutorial
buy-and-brew flow, plus direct game_eval calls to force day advances, AVI
raids, and sales, since OS-level click simulation is unreliable in this
environment. All 37 GDScript unit tests pass (test_run). This is a
follow-up to playtest_notes.txt (2026-09-11) and playtest_notes_2.txt
(2026-09-12) — this pass focuses specifically on what changed since:
starting money 100 -> 20 EUR, the removed tax model + fixed per-style
prices, float-precision money, and the brand-new three-ending game-loop
(Busted / Bankrupt / Survived) including the just-added "continue past
Survived" option. No unaddressed crashes or script errors found during
normal play; two crashes were produced but only by test code calling
internal handlers directly in an unnatural way a real player cannot
reach (details below, not counted as bugs).


ENDING SYSTEM — ALL THREE ENDINGS VERIFIED LIVE
==================================================
File: src/classes/brewery.gd (trigger_ending, check_bankruptcy,
_check_for_avi_raid), src/autoload/time_manager.gd (_check_survival_ending),
scenes/ui/game_end_window.gd.

Busted (3rd AVI raid): forced risk to the 100 threshold three times in a
row. Raid 1 and 2 fined 30% of current cash and reset risk without ending
the run (raid_count incrementing correctly); raid 3 correctly set
game_has_ended, paused the tree, and showed "BUSTED!" with the right
flavor text and end-of-run stats (days survived / final reputation /
lifetime bottles sold). Only "Uusi yritys" was shown — no continue option,
as intended for a genuine dead end.

Bankrupt (money <= 0 AND zero bottles in inventory): tested two ways.
(1) check_bankruptcy() called directly after zeroing money and clearing
inventory — fired correctly. (2) The real, reachable path: bought an
ingredient that spent the last of a low cash balance via the normal
GUISignals.buy_ingredient flow — Brewery._on_buy_ingredient's trailing
check_bankruptcy() call caught it correctly and showed "KONKURSSI!".
(3) A more interesting real scenario: a player at 0 EUR cash holding
bottled stock as their only remaining value, then hit by an AVI raid —
the raid confiscates the entire inventory as part of its normal
punishment, so check_bankruptcy() (called at the tail of
_check_for_avi_raid when raid_count hasn't yet reached BUSTED_RAID_COUNT)
correctly recognizes "no cash, and the raid just took the only thing that
could have raised any" and ends the run as Bankrupt, not just another
survived raid. This is exactly the intended interaction between the two
failure conditions and it works.

Survived (day 15 reached with reputation >= 20 and money > 0): set
current_day=14, reputation=50, money=50, then advanced one real day via
TimeManager.force_advance_day() (the same call the day timer/dev "day"
command use) — the survival check at the end of _advance_day() correctly
fired, showing "LEGENDA!" with the right flavor text and stats. The
continue button ("Jatka pelaamista (ei tilastoihin)") appeared alongside
"Uusi yritys", correctly rendered in-game (confirmed via screenshot).


CONTINUE-PAST-SURVIVAL — VERIFIED END TO END
================================================
File: scenes/ui/game_end_window.gd (_on_continue_button_pressed),
src/classes/brewery.gd (has_continued_past_survival),
src/autoload/time_manager.gd (_check_survival_ending).

Pressing continue on the Survived screen: unpaused the tree, cleared
game_has_ended back to false, and set has_continued_past_survival to
true, all without reloading the scene — the run's existing state (money,
day, inventory, reputation) carried forward untouched, confirmed live.

Re-checked afterward that the loop doesn't re-fire the same ending:
forced another real day advance past day 15 on the continued run —
_check_survival_ending's new `or brewery.has_continued_past_survival`
guard correctly skipped it, day advanced normally with no popup.

Confirmed busted/bankrupt can still end a continued run later (since
game_has_ended was reset, just not has_continued_past_survival): forced
a bankrupt condition on the same continued-past-survival run and it
correctly fired "KONKURSSI!" — continuing past the good ending doesn't
make the run unkillable, it just retires that one ending permanently.

Save/load persistence: has_continued_past_survival is @export'd
specifically so a continued run survives a save/reload, per its own
docstring. Verified directly — saved mid-continued-run (day 16,
has_continued_past_survival=true, game_has_ended=false), reloaded via
SaveManager.load_game(), and all three fields came back exactly as
saved, with the tree correctly unpaused and no ending re-triggering on
load. This was the one part of the feature that hadn't been exercised
yet before this report and it holds up.


TWO CRASHES FOUND — BOTH TEST-HARNESS ARTIFACTS, NOT REACHABLE BUGS
========================================================================
Worth documenting since they did produce real GDScript runtime errors,
even though neither is something a player can trigger:

1. Calling GameEndWindow._on_restart_button_pressed() twice back-to-back
   in the same synchronous script (no frame yielded in between) produced
   "Invalid assignment of property or key 'paused' ... on a base object
   of type 'null instance'" — a second ending fired on a GameEndWindow
   instance whose scene had already begun tearing down from the first
   restart's change_scene_to_file() call, so get_tree() returned null.
   Real players cannot reproduce this: the restart button calls hide()
   as its first action, so it cannot be clicked a second time before the
   scene actually swaps out.
2. A related variant produced "Invalid access to property or key
   'has_continued_past_survival' on a base object of type 'bool'" — this
   one was purely a mistake in my own eval script (SaveManager.load_game()
   returns a bool success flag, not the loaded Brewery — I'd assumed the
   latter). Not a game bug at all; confirmed by re-reading
   src/autoload/save_manager.gd and rewriting the test correctly, which
   then passed cleanly (see persistence check above).

Neither required any source change. Both were cleared by stopping and
relaunching the play session.


ECONOMY AT THE NEW 20 EUR STARTING BALANCE
==============================================
File: src/classes/brewery.gd:40 (money default), the fixed-price
.tres overrides on all 22 beer styles.

The tutorial's guaranteed recipe (3kg Pilsner malt @ 2 EUR/kg + 1 baking
yeast @ 2 EUR) costs exactly 8 EUR. Played it via the real GUISignals
buy/add-to-table/brew flow: money went 20 -> 12 (after buying) -> 10
(after the 2 EUR bottling/label cost on brewing), leaving a real but not
razor-thin cushion. Brewed batch scored quality 1.0 as expected (the
Kotikalja EBC-window fix from the last report still holds). A single
2-bottle sale to a generic customer at Kotikalja's fixed 1.0 EUR/bottle
price, with the tip floor, brought money to 13 EUR — confirms the loop is
immediately playable and not a coin-flip on whether the tutorial itself
is affordable.

This is a much tighter margin than the old 100 EUR start (previously ~12
EUR of "profit" on the first batch was noise against a 92-EUR cushion;
now it's the difference between having 10 EUR or 22 EUR of runway). That
tightness is clearly the intent — bankruptcy is now a real ending, and
the docstring on Brewery.money says as much — and it plays exactly as
described: the first few decisions (do I buy extra malt for a bigger
batch, or stay safe) now carry real weight instead of being
consequence-free. No changes needed here; flagging it as confirmed-working
rather than a gap.

UI / DISPLAY CHECKS
=======================
- Top panel money readout, sale receipt totals, daily bills log line, and
  both the Busted and Bankrupt/Survived end screens all render with clean
  one-decimal EUR formatting (e.g. "13.0 €", "48.0 €") — confirmed via

- One cosmetic-only artifact, not a real bug: firing three AVI raids back
  to back within the same test script (impossible in real play, since
  each raid needs risk to climb back to 100 through actual gameplay in

  at once. This is a rendering side effect of forcing events far faster
  than any real player interaction could, not something reachable in
  normal play; not filing it as a bug, just noting it was observed.


VERDICT
==========
Everything targeted by this pass — the three endings, the new continue-
past-Survived option (including its save/load persistence, which hadn't
been checked before), the interaction between AVI raids and bankruptcy,
the lowered starting balance, and the fixed price ladder — works exactly
as designed. No source changes were needed as a result of this playtest;
the two crashes encountered were both artifacts of testing internal
methods directly rather than through reachable player input, not real
bugs, and are documented above for the record rather than as open items.
